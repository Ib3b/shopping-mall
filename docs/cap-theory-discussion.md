# CAP 理论与分布式系统讨论记录

> 2026-05-16 苏格拉底式讨论整理
> 从 CAP 理论出发，一路推导到微服务与集群的分布式本质。

---

## 一、CAP 理论的核心问题

**分布式系统与单机的本质区别**：每台机器看不到全局，节点间通信不可靠。这引出了 CAP 理论要讨论的核心问题——当网络故障时，如何在 Consistency（一致性）和 Availability（可用性）之间取舍。

### 关键推导

```
分布式基础事实：网络一定会断（Partition 强制选择）
         ↓
分区发生时只有两条路：
  ├─ CP：停服务，保一致     → 数据干净，但服务不可用
  │    例子：ZooKeeper, etcd
  │    感觉：大家都不要动，没有变化就一致了，但服务也停了
  │
  └─ AP：继续服务，事后同步   → 服务可用，但数据不一定一致
       例子：DNS, CDN
       感觉：各节点独立处理，用时间换可用性
```

### 为什么没有 CA 系统？

因为 P（分区容错性）是分布式的基础事实，无法抛弃。不解决分区问题的系统就不是分布式系统。

### 结论

CAP 不是三个选两个，而是在 P 必然发生的前提下，**在 C 和 A 之间做选择**，本质上就是在选一个你能承受的矛盾。

## 二、最终一致性

### 冲突检测手段

| 手段 | 原理 | 例子 |
|------|------|------|
| 版本向量/时钟 | 每个节点维护版本号，交换时发现谁的更新被覆盖 | Amazon Dynamo |
| 离线对账 | T+1 拉全量数据做比对交易 | 金融系统 |
| 校验和/哈希树 | 定期比较 Merkle 树根哈希，快速定位不一致块 | Cassandra |
| 操作日志审计 | 逐条比对各节点的写入日志 | 金融监管 |

### 冲突合并策略

| 策略 | 适用场景 |
|------|----------|
| 最后写入胜出（LWW） | 简单场景，接受少量数据丢失 |
| CRDT | 协作编辑、计数器等天然可合并的数据结构 |
| 多版本保留 + 业务合并 | 类似 git，保留两个版本由业务层决策 |
| 补偿事务 | 发现错误后发一条"冲正"记录（如银行调账） |
| 业务自定义 merge 函数 | 告诉系统两笔冲突记录如何合成一笔 |

### 关键认知

冲突检测和合并没有通用的正确答案。**"谁对谁错"最终是业务问题**，技术层面提供工具（CRDT、版本向量、最后写入胜出），但决策权在业务层。成熟的分布式系统采用分层设计——引擎层保证不丢数据，冲突策略以插件或回调形式交给业务层自定义。

## 三、集群 vs 微服务

### 两种架构的分布式本质

| 对比维度 | 集群 | 微服务架构 |
|----------|------|------------|
| 存储 | 共享持久层（共用一个库） | 各服务独立数据库 |
| 一致性模型 | 强一致（CP） | 最终一致（AP） |
| 扩展能力 | 有限，瓶颈在存储层 | 独立部署、独立扩缩容 |
| 分布式问题 | 共享存储成了单点、锁竞争 | 跨服务数据靠事件驱动同步 |

### 关键认知

集群不是"没有分布式问题"，而是**把一致性问题外包给了共享存储层**，代价是可用性和扩展性受限。

微服务则是反过来，**把一致性拿到业务层自己处理**，换来独立灵活部署的能力。

### 同一枚硬币的两面

```
              都是分布式系统
              都面对 CAP 取舍
              只是选择的维度不同

集群：在存储层解决一致性问题
微服务：在业务层解决一致性问题
```

---

## 四、总结

1. **CAP 理论的核心**：分布式系统中网络一定会出故障，此时你必须在一致性和可用性之间做选择，没有完美的方案
2. **最终一致性的本质**：用时间换可用性，但引入了冲突检测和合并的问题，而这些问题最终是业务问题
3. **集群 vs 微服务**：两者都是分布式系统，都面临 CAP 取舍，只是把问题放在了不同层次解决——集群交给存储层、微服务交给业务层
4. **没有银弹**：分布式系统没有完美的答案，只有权衡。成熟的系统是分层设计——底层保证基础设施的可靠性，冲突策略留给上层业务自定义。
